# 段階的な制作計画

対象: Meta Quest 3のPCVR、Unity6000.3.15f1、2m四方。180秒の時間上限は2026-09-23のユーザー決定で当面外す（まずしっかり遊べることを優先。再導入はユーザー判断）。
既存のVR_demo_plan_v0.1.mdは企画の根拠・過去の提案として維持。**2026-09-24 以降の体験の企画は `VR_demo_plan_v0.2.md` を正とする**（部屋の回転、ワンルーム、音による死の痕跡、問題は保留。段階4の「2場面から5場面」は「部屋の種類を増やす」に読み替える）。この文書は現在の実行計画。

| 段階 | 実装/確認 | 完了条件 |
| --- | --- | --- |
| 1: 移行と基盤 | コード/企画の保存、純粋モデル検証、管理スクリプト検証、CI、002/003レビュー | 同じSHAのSol/Sonnet独立レビューと交換、ローカル検証、作業ブランチpush/ドラフトPR。Unity/実機が残れば明記 |
| 2: Quest3で1場面 | XR準備、床/頭/手、遮蔽/出口、暗転/音、3回死亡と3回Play | 身体を再配置せず反復できる、開始前の準備ゲート、操作到達範囲、PC観客の攻略秘匿、1セッションの実時間の実機記録（180秒上限は当面なし） |
| 3: 体験の調整 | 初回のミスリード、因果の手がかり、最後の達成感、追跡停止/再準備 | 初見評価で死に戻りの理解と自力突破が成立、安全・時間に関する問題を解消 |
| 4: 2場面から5場面 | 共通操作+シナリオデータ。1人の周回中はシナリオ固定 | 場面ごとに攻略成立。観戦後の別場面で体験を検証してから5場面へ |
| 5: 展示運用 | 観客画面、運営操作、匿名履歴、振返り/QR | 待機客のネタバレ評価、匿名データ運用、復旧手順。オンライン多人数は別途合意 |

初期は同一Unity内C#通信とローカルJSONのみ。外部バックエンド、ネットワーク同期、自由戦闘を初段階へ足さない。
各段階を小さなIssueへ分割し、実装→意味のある自動テスト→独立レビュー→報告交換→ドラフトPR。失敗時は対象段階へ戻り、2案で不一致ならOpus優先で判断を依頼。
依存更新はバージョン検出/提案を行い、自動適用しない。公開版とlock解決、Unity/API互換性、実機回帰を別Issueで確認する。
CIはまずPython管理検証とUnity不要のC#モデル検証。Unityライセンス/専用runnerが用意できるまでUnity統合buildを合格扱いにしない。CIの同一PR旧実行キャンセルと最小権限を用いる。
